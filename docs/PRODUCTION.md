# Production procedure for Codex

The local code journals and verifies state. Codex provides filmmaking judgment, calls registered MCP tools, watches media and continues the project. There is no background LLM, browser-login clone or new cloud service.

## Plan

1. Extract audience, purpose, platform, aspect ratio, final runtime, style, subject, story beats, audio/dialogue, supplied assets and caps. Also settle the project/output folder and **clips only versus assembled final film** now; record assembly authorization once in `authorization.assemble`. Inventory the supplied files before creating references. Ask only about missing decisions that materially change the film or spending; infer reversible details.
2. `python flow.py init <slug> --title "…"` creates a per-film folder. Use `--directory "Exact project name"` when the user requests a named workspace subfolder; the slug remains lowercase and the directory must remain inside this workspace. Fill the manifest and planning documents. Store the exact user production request in `authorization.request`, set `produce:true` only for a production request, and record total image/video output caps including variants/revisions. Planning requests leave it false. Verify the configured browser download location before the first submission and check the actual first returned path; copying an outside download afterwards does not satisfy a requirement to save directly inside the project.
3. Give assets A01… and shots S01… stable IDs. Record scene, purpose, screen seconds, supported generation duration, start/end state, framing, one readable action, camera, audio, reference roles and visible acceptance criteria. Specify trims in seconds. Dependency order comes from `references[].unit` and `depends_on`; manifest shot order is edit order.
4. Choose text-to-video for scenes without exact identity, ingredients for recurring identity in a new composition, frames for exact boundary composition, extension only for one continuous Veo shot. Check the operation/model table. Keep prompt text separate from settings and editorial notes. Put exact graphics/copy into the edit plan.
   For conversation shots, use the structured `dialogue` contract in `templates/dialogue-shot.json`. The runner compiles one quoted line and explicit sole-speaker ownership into the request. Keep the base prompt visual/performance-only. Reserve opening silence and a final closed-mouth settling hold inside the actual **edit window**; the listener cannot speak even the first word or prepare an answer at the previous shot's endpoint. See the [first-word procedure](VIDEO_RECIPE.md#assign-every-word-to-one-speaker).
5. Run `validate` and `dry-run`. Quote image outputs, video outputs, planned variants, revision reserve and generated versus edit seconds separately. A credit price remains unknown unless actually quoted by Flow. Count all attempted outputs conservatively against the cap, including failed/uncertain submissions. If the stated cap cannot fund an affected downstream revision, stop before additional submission and ask for the specific cap change.

## Preflight and production loop

1. Call registered `flow_status({site:"flow"})`, save the entire raw tool result as a UTF-8 JSON file. It must be fresh (runner rejects status files older than two minutes). With MCP unavailable, use `flow-auto status --site flow --json` through normal host approval. This uses the same installed bridge and Edge extension.
2. Separately inspect the visible signed-in Edge Flow tab: correct project URL/ID, requested resolution, selected account/model availability, enough account allowance without purchases, and open Flow Connector side panel. Status alone does not expose the project URL or prove visibility. Use computer-use autonomously when available; ask for factual setup confirmation only if it cannot actually be inspected. Save evidence with `preflight --source agent_ui|user_confirmation`; never claim a user observation was an agent inspection. Create/choose a project once, then reuse it. Preflight expires after 15 minutes and after relevant UI/project changes. At each completed-unit boundary run `preflight-check`: its two-minute warning lets Codex renew proactively or bundle setup confirmation into an already-needed first-speaker playback review. Do not wait until `prepare` fails, extend the timer from status alone, or recycle an old confirmation as a new observation.
3. Disconnected/stalled: save state, ask the user to open Flow in Edge, sign in, enable Flow Connector, keep the window/tab and side panel visible and confirm before rechecking. Relay specific blocked-access steps from the connector. At a cooldown poll/wait; at a daily/account limit stop and report only returned reset times/upgrade links. Do not upgrade, buy credits, accelerate pacing or switch providers.
4. Pick one ready unit. All essential referenced units must have actual reviewed selected files, and must not be stale or awaiting revision. Inspect A01 before S01; inspect the first look-establishing clip before any following shot. Batch only independent work within limits; this runner deliberately submits sequentially by default.
5. For MCP: run `prepare PROJECT UNIT --transport mcp --status-file FILE`. It writes `manifest.json` and immutable `takes/<take>/request.json` **before** any call, including the final compiled prompt and payload hash. Run `payload PROJECT TAKE` and parse its ASCII-escaped JSON as the tool arguments. This exports the exact saved object, verifies ledger/hash equality and rejects U+FFFD; it does not reconstruct prompts or submit. Use `--verify-file FILE` to compare a candidate if needed. Never retype or rebuild dialogue through Windows console text. Call `flow_generate` exactly once. Save the complete response immediately, then `record PROJECT TAKE --response FILE`. Never call `prepare` again for an already-journaled request. If reading/exporting JSON is truncated, repeat only that read with sufficient output budget before the first tool dispatch.
6. Pending ID: keep calling `flow_get_job({job_id:ID})`, save and record each response until terminal. Each tool wait is bounded (~40 seconds); send short useful progress updates when needed. A slow generation/cooldown is expected. Do not invoke `flow_generate` again to poll.
7. CLI fallback: `run-cli PROJECT UNIT` performs the same fresh status check and write-ahead journal, calls the installed Node CLI with a native argument array and `shell=False`, and records its returned ID. No shell string interpolation, no `cmd /c`, no retyping prompts or paths. `resume --cli` lists/gets without submission. Failed commands/timeouts leave the existing intent pending. Do not chain retry commands.
8. `record` preserves responses and original paths, copies returned downloads into descriptive immutable take filenames and hashes them. `done` plus a missing/empty file or wrong output count becomes `missing_download`, not success. Source labels/notes are preserved where the CLI exposes them. MCP messages/quality warnings are preserved verbatim. An immediate complete MCP response can lack a job ID; reconcile it before further generation.
   A failure is a **connector report**, not proof that no browser asset exists. Before a retry, cap-increase request, omitted shot or shorter-film proposal, check the visible project and exact download folders as well as job records. A playable clip may still exist in the visible Flow project despite connector failure reports. Do not rotate prompts to evade a genuine provider restriction. If a legitimate supplied-fictional-character request is flagged, first check for an already-created asset; any genuine revised attempt remains subject to caps and the ordinary journal.
9. `probe PROJECT TAKE --fit-shortfall` checks downloaded video and can journal an end-trim reduction of at most 0.15 s for nominal eight-second clips that are slightly shorter. It uses video-stream duration, preserves raw media/request/settings, updates edit totals, and invalidates affected trim reviews; it never pads, speeds up or removes words to force a runtime. Larger shortages, wrong ratio/resolution or missing required audio need a deliberate decision. The probe fully decodes files and creates opening/action/ending previews, plus an early speech preview for configured dialogue. Inspect frames **and play/listen** to the first 1–2 seconds at the actual edit-in, complete line and final second. Record who speaks the **first audible word**, every listener's silence, exact words, voice and lip sync. A plausible still or non-silent audio stream is insufficient.
10. Fill a separate review JSON using `templates/review.json`; include concrete observations and unperformed checks. Use `review … --select` only when the take meets its acceptance criteria. Still images alone establish no motion/audio quality. The runner checks that review evidence exists, but cannot establish whether a person or agent truly inspected it. Codex must do the inspection.
    For configured dialogue, selection requires explicit `dialogue_checks`: correct expected speaker and first word, that speaker actually delivering the first word, a silent listener, the exact line, and scoped agent/user playback evidence. A listener speaking the opening word fails even if the rest sounds correct. Review the first speaking take of **each character** before dependent speaking work. If playback tools are unavailable, ask the user focused factual quality questions; after first-speaker acceptance, independent remaining clips can be reviewed together. Never record unperformed checks as passed to avoid an interruption.
11. For a frame input, the runner extracts the specified timestamp from the actual selected source take, saves it under `assets/frames/<take>_<seconds>.png` and records the take/time/path in the next request. Inspect the extracted frame before submitting the dependent clip. If an essential extracted frame needs closer inspection, extract/inspect it before `prepare`; an already-journaled request must not be sent after its inputs change.

## Resume after interruption

1. Read manifest and raw responses first. Call `flow_list_jobs`, save its raw result, and run `resume PROJECT --jobs-file FILE`. For the CLI fallback, `resume PROJECT --cli` lists full jobs and gets each known ID. Neither command submits anything. Verify existing selected files still exist and match hashes before using them.
2. Known ID: poll that ID, record actual status and returned files. Terminal `done` is not enough without verified downloads. Recover missing downloads from connector results or the exact token-bearing download subfolder; preserve original paths. Never regenerate to fix an uninspected download.
3. Unknown ID after a saved intent: match the full CLI prompt/mode/unique `downloadSubfolder`, or a completed MCP row's unique token-bearing path. Exactly one strong match can bind the ID. Multiple/no strong matches leave it pending. MCP's prompt prefix and timestamp alone are insufficient.
4. A pending MCP candidate can be polled read-only with `flow_get_job`; save all evidence. Completed paths may reveal the token and allow reconciliation. Inspect the exact Downloads subfolder if needed. An orphan file without a proven job association is evidence to preserve, not permission to generate again. Do not infer non-submission from an empty/truncated job list. No idempotency key exists at the connector, so an ambiguous crash can require waiting or user-assisted identification rather than an automatic retry.
5. If an ID is independently verified, `record --job ID` can associate a raw result that omits it. Never guess. If code stopped before sending but after journaling, the same uncertainty rule applies. Do not delete the pending take, reset the manifest or create a revision to bypass it.
6. After reconciliation, refresh preflight/status, review completed work, then prepare only a genuinely unfinished ready unit. Preserve the same Flow project. A stale `.flow.lock` may be removed only after verifying no runner process is active; inspect the saved intent first.

## Recover an existing Flow asset

Use `recover PROJECT UNIT --file FILE --provenance-file JSON` after an existing clip is downloaded into the project. The [provenance template](../templates/recovery-provenance.json) requires `existing_asset:true`, this film's recorded `source_project_url`, and concrete source/download evidence. Include the visible clip label/URL if available. A filename alone is not a queue-job association.

Recovery creates `S05_R01` (or the next R-number), copies/hashes the original, records no generation prompt/model as verified, and leaves its queue-job ID null. It preserves previous takes and failure reports, spends **zero** generation outputs, and cannot clear a different ambiguous pending submission. Exact duplicate hashes are rejected. Probe, play/review, then select the recovered asset through the same checks as other clips. It can be assembled directly in the original project without an ad hoc editorial clone. Do not retrofit unknown queue IDs or relabel failed jobs as successful to make the ledger look tidy.

```powershell
python flow.py recover my-film S05 --file "projects/my-film/downloads/closing.mp4" --provenance-file "projects/my-film/recovery-source.json"
python flow.py probe my-film S05_R01 --fit-shortfall
python flow.py review my-film S05_R01 --evidence-file "projects/my-film/recovered-review.json" --select
```

## Autonomous decisions and real limits

Within the recorded brief and caps, continue reversible planning, safe payload export, job polling, small duration fits, file recovery and checks without another blanket permission question. Record inferred creative details. Reuse explicit final-film/assembly authorization from intake. Ask only for material scope/cap changes, genuinely missing source/setup information, or playback that the agent cannot perform.

If desktop inspection fails at startup, diagnose once and use honest user evidence while unavailable; repeatedly retrying the same broken helper does not improve autonomy. Bundle essential setup checks with quality review and keep the 15-minute/fresh-status safeguards. A `duplicateInstalls` flag deserves one diagnostic note, not automatic extension updates/reloads while a job is active. Do not buy credits or repair OS security settings as part of production.

Automatic approval rejection, provider refusal, download failure and uncertain acceptance are different states. Preserve their raw evidence. A pre-execution rejection must not be relabelled as a Flow job; correct and verify any transport problem without dispatching, then obey the pending-request/no-repeat rule and any specific required exception. No helper automatically retries a generation or bypasses approval review.

## Targeted revision

Use `revise PROJECT S03 --prompt-file FILE`. The original takes and selected file remain. The command updates the planned prompt, marks the unit as needing a take and lists dependent units. Prepare a new take only within the existing cap. For a changed cup silhouette strengthen the reference/use a start frame; for incoherent hand motion simplify the action. Change only the relevant input.

After the new take is reviewed and selected, all transitive dependents are flagged stale. A shot using a replaced take's frame cannot be selected again as current. Regenerate only affected shots after their current references are selected; new frame filenames include the new source take. Replacing S01 can consume both a new S01 and a new S02; one reserved video may not cover that. A new selection retains the previous media and review record.

## Deliver

Deliver actual selected file links in manifest edit order, descriptive filenames/take IDs, verified available durations, exact in/out trims and total planned edit time. State what was inspected and any motion/audio/manual review outstanding. Do not call a raw clip or dry-run placeholder an assembled film.

On an explicit assembly request, `assemble PROJECT` trims selected shots, normalizes video/audio, concatenates, probes and decodes the actual export, and writes `deliverables/<unique-export>/delivery.json`. Missing source audio becomes silence unless `audio_required:true`, in which case assembly stops. Native audio is concatenated; separate music, dialogue replacement, captions, logos or audio crossfades require an explicit edit plan and FFmpeg/editor work before delivery. Inspect/play the resulting export for cuts, sound and pacing. The automatic report deliberately leaves that final playback review outstanding.

If using manual Flow Scenebuilder, identify actual Flow clip labels, order, source take IDs and trim points. No timeline/export MCP capability is exposed on this installation. Verify any manually exported file before reporting a finished export.
